# mono-agent

Агент, який відповідає на питання про власні гроші й про правила банку, спираючись
на живий API monobank і на 18 публічних документів банку — і не вигадує відповідь,
коли даних немає.

> «Скільки я витратив учора?» · «Що з моєю банкою на відпустку?» ·
> «Я загубив картку, що робити?» · «Яка комісія за переказ в інший банк?»

Два джерела правди, і жодного слова від себе: цифри беруться з виписки, правила —
з чинних Умов і Тарифів із посиланням на пункт. Питання, відповіді на яке немає в
жодному з двох джерел, закінчується словами «цього немає», а не правдоподібним
переказом.

Задача навмисно така, яку **не закрити одним викликом API**: у monobank виписка
запитується не за назвою картки, а за `id` рахунку, і цей `id` віддає лише
окремий метод. Тому кожна відповідь про витрати — це ланцюжок мінімум із двох
кроків, де результат першого є аргументом другого.

```
list_accounts()  →  id рахунку  →  get_statement(account, from_ts, to_ts)  →  відповідь
```

## Як запустити

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

У `.env` вписати два значення:

- `ANTHROPIC_API_KEY` — з console.anthropic.com, `ANTHROPIC_BASE_URL` лишити порожнім
- `MONO_TOKEN` — на https://api.monobank.ua (вхід за QR через застосунок monobank,
  там же кнопка отримання персонального токена)

Ключі читаються **тільки з `.env`**, у коді їх немає, `.env` у `.gitignore`.

Далі — база документів. Корпус уже лежить у `knowledge/`, але векторний індекс
треба побудувати локально (перший запуск тягне ваги моделі ембедингів — 2,1 ГБ
у кеші, ключа для неї не потрібно):

```bash
python search.py --build      # ~100 с на MacBook, одноразово
```

Щоб перезібрати сам корпус із сайту банку — `python fetch_knowledge.py`.

### Інший постачальник моделі

Агент говорить протоколом Anthropic Messages, тому працює з будь-яким сервісом,
який цей протокол реалізує — код при цьому не змінюється. Наприклад QwenCloud:

```
ANTHROPIC_API_KEY=<ключ QwenCloud>
ANTHROPIC_BASE_URL=https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic
ANTHROPIC_MODEL=qwen3.8-max
```

Змінна називається `ANTHROPIC_API_KEY`, бо означає «ключ до Anthropic-сумісного
API», а не «ключ, виданий Anthropic». Порожній `ANTHROPIC_BASE_URL` означає
стандартний `api.anthropic.com`.

`.env` читається з `override=True`: якщо в оточенні вже є `ANTHROPIC_BASE_URL`
(його виставляють деякі інструменти), налаштування з файлу мусить перемагати,
інакше запити тихо підуть не туди.

### Команди

```bash
python run.py "скільки я витратив учора"
python run.py "що з моєю банкою" --verbose      # показати сирі відповіді інструментів
python run.py "скільки я витратив за літо" --max-turns 3
python run.py "порахуй витрати на каву" --tools v1
python run.py "скільки я витратив учора" --mask  # приховати суми та id
python run.py "я загубив картку, що робити"      # питання до бази документів
python run.py "як оформити пенсію" --rag naive   # база знань без запобіжників
```

| Прапорець | Навіщо |
|---|---|
| `--tools v1\|v2` | варіант описів інструментів (див. челендж A) |
| `--rag naive\|guarded` | пошук по документах без запобіжників або з ними |
| `--max-turns N` | ліміт кроків циклу |
| `--model NAME` | інша модель |
| `--verbose` | повні відповіді інструментів, не тільки підсумок |
| `--mask` | замінити цифри в сумах і скоротити `id` — для публікації прогонів |
| `--router` | маршрутизатор: класифікує запит і веде до вузького спеціаліста (модуль 4) |

`--mask` вимкнено за замовчуванням: щодня потрібні справжні числа. Маска чіпає
лише друк — модель у будь-якому разі отримує реальні дані, тому замаскований
прогін лишається справжнім прогоном, а не переказом.

Усі сцени разом відтворює `demo.py`:

```bash
python demo.py          # усі сцени
python demo.py 3 6      # тільки вибрані
python demo.py --mask   # з прихованими сумами
```

| Сцена | Що показує |
|---|---|
| 1 | щасливий ланцюжок `list_accounts` → `get_statement` |
| 2 | `tool_error`: недійсний токен monobank |
| 3 | `turns_exhausted`: питання про літо при ліміті 3 кроки |
| 4 | `api_error`: навмисно зіпсований ключ |
| 5 | `no_tool_used`: питання про самого агента |
| 6 | челендж A: той самий запит на описах `v1` і `v2` |
| 7 | порожній період: `count: 0` замість вигаданих операцій |
| 8 | питання до бази документів, поставлене іншими словами |
| 9 | ембединги проти BM25 на однакових даних (без моделі) |
| 10 | питання не з бази на `naive` і `guarded` |
| 11 | роутер: три типи запитів → три вузькі спеціалісти |
| 12 | петля критика: явний ліміт спроб `submit_answer`, окремий від `MAX_TURNS` |

## Який API використано

[monobank personal API](https://api.monobank.ua/docs/), автентифікація заголовком
`X-Token`. Факти нижче звірені зі вбудованою OpenAPI-специфікацією (версія `v250818`),
а не взяті з памʼяті.

| Ендпоінт | Що дає | Обмеження |
|---|---|---|
| `GET /personal/client-info` | рахунки (`id`, `type`, `currencyCode`, `balance`) і банки (`jars`) | 1 запит / 60 с |
| `GET /personal/statement/{account}/{from}/{to}` | виписка за період | 1 запит / 60 с; вікно ≤ 2 682 000 с (31 доба + 1 год) |

Дві деталі API визначили дизайн агента:

- **суми приходять у мінімальних одиницях** (копійках), відʼємні — витрати;
  ділення на 100 лишається за моделлю, тому в кожній відповіді інструмента
  є явна примітка про формат;
- **помилки треба читати за HTTP-кодом**, тіло містить `errorDescription`.
  Ліміт 1 запит/60 с означає, що `429` — не екзотика, а звичайний робочий стан,
  який агент мусить пояснити людині.

# Модуль 1 · Основа: ланцюжок інструментів

## Ланцюжок

| Інструмент | Аргументи | Повертає |
|---|---|---|
| `list_accounts` | — | рахунки і банки з `id`, валютою, балансом |
| `get_statement` | `account`, `from_ts`, `to_ts` | операції за період |

`get_statement` не можна викликати першим, і це забезпечено **кодом**, а не
проханням в описі: інструмент приймає лише той `id`, який справді прийшов від
`list_accounts` у цьому ж прогоні. Будь-що інше — вигаданий `id`, назва картки,
`0` з документації monobank — повертає `unknown_account`. Реєстр відомих `id`
очищається на початку кожного прогону, тож ланцюжок доводиться проходити щоразу.

## Агент не вигадує даних

Порожній період — це `count: 0` з приміткою, а не помилка: розрізняти
«операцій не було» і «дані не вдалося отримати» агент зобовʼязаний уголос.
Виписка довша за 150 операцій позначається `truncated` з попередженням, щоб
неповна сума не видавалась за повну. У системному промпті числа й назви
дозволено брати виключно з відповідей інструментів.

## Стани агента

Цикл завжди завершується одним із станів, і це **повернене значення**,
а не побічний ефект — викликач розгалужується на ньому, а не вгадує з тексту.

| Стан | Коли |
|---|---|
| `ok` | ланцюжок пройдено, відповідь спирається на дані |
| `tool_error` | жоден виклик інструмента не вдався |
| `turns_exhausted` | вичерпано ліміт кроків |
| `api_error` | збій моделі: ключ, мережа, ліміт |
| `no_tool_used` | модель відповіла, жодного разу не звернувшись до банку |
| `critic_exhausted` | `submit_answer` відхилено `MAX_CRITIC_ATTEMPTS` разів поспіль (модуль 4) |

Прогін, який оговтався після невдалого виклику, завершується як `ok`, але зі
списком `failures`: часткова халепа лишається видимою, не стаючи фатальною.

## Ліміт кроків

`MAX_TURNS` (за замовчуванням 6) обмежує кількість обертів циклу. Вичерпання —
не тихий обрив: цикл робить фінальний виклик **без інструментів** і просить
модель підсумувати зібране та назвати, що лишилось недоступним. Якщо падає і
цей виклик — повертається фіксована фраза. У будь-якому разі користувач
отримує відповідь і стан `turns_exhausted`, а не мовчання.

ендпоінт — код той самий, що піде з ключем Anthropic. Суми і `id` приховані
прапорцем `--mask`; модель у прогоні отримувала справжні дані, маска чіпає
лише друк.

# Модуль 1 · Челендж A: опис інструмента = поведінка агента

Знайти запит, на якому агент плутає аргументи, полагодити це **описом
інструмента**, і показати прогони до і після.

**Запит:** «Скільки я витратив за останні три місяці?»

**Аргумент, який плутається:** `to_ts` у `get_statement`. monobank віддає
виписку максимум за 31 добу + 1 годину (2 682 000 с). Опис `v1` про це мовчить —
там сказано лише «Останній час виписки», — тож агент замовляє одразу весь
тримісячний період.

**Що змінюється між варіантами.** Виконуваний код інструментів **однаковий**:
та сама функція, та сама валідація, той самий HTTP-запит. Відрізняється рівно
текст опису — тому різниця в поведінці пояснюється описом, а не прихованою
правкою логіки. Перемикається прапорцем `--tools v1|v2`.

### Перша гіпотеза не підтвердилась

Спершу я очікував іншої помилки: специфікація monobank дозволяє передати
`account="0"` («дефолтний рахунок»), і `v1` цю можливість згадує. Здавалося,
агент спокуситься й пропустить `list_accounts`. Прогін це спростував — на

## Висновок

Вирішив **один рядок** — згадка максимального вікна в описі `to_ts`:

```
Максимальне вікно — 2682000 с (31 доба). Довший період розбивати на кілька викликів.
```

До нього агент дізнавався про обмеження єдиним доступним способом — впираючись
у нього, і платив за це пʼятьма марними викликами та зайвими токенами. Після —
обмеження стало частиною умови задачі ще до першого виклику.

Спостереження, яке варте окремої уваги: агент **не переносив** засвоєну помилку
між рахунками. Отримавши `window_too_large` на першому, він повторив той самий
завеликий діапазон ще чотири рази. Тобто помилка інструмента вчить гірше, ніж
опис: опис читається один раз до дії, а помилку доводиться зустріти окремо в
кожній гілці міркування.

Практичний висновок для будь-якого інструмента: **обмеження треба писати в опис
параметра, а не сподіватись, що агент вивчить його з відповіді про помилку.**

### Сюрприз у форматі: це не PDF

Перелік чинних редакцій віддає `GET /api/info/versioning-docs/{slug}`, самі файли
лежать за `https://monobank.ua/pdf/{fileName}`. Але **10 із 18** цих «pdf» не
відкриваються PDF-бібліотекою:

```
pypdf.errors.PdfReadError: Trailer cannot be read: '/Type'
```

Перші байти файлу пояснюють чому:

```
30 83 29 99 a4 06 09 2a 86 48 86 f7 0d 01 07 02
                  └─ OID 1.2.840.113549.1.7.2 = PKCS#7 signedData
```

Це не PDF, а контейнер із кваліфікованим електронним підписом, усередині якого
лежить PDF. Банк підписує документи КЕП, і на сайт викладає саме підписаний
контейнер із розширенням `.pdf`. Розпаковується він тривіально — вирізанням
від `%PDF-` до останнього `%%EOF`:

```python
def unwrap_signature(raw):
    if raw.startswith(b"%PDF-"):
        return raw
    start = raw.find(b"%PDF-")
    end = raw.rfind(b"%%EOF")
    return raw[start:end + 5] if end > start else raw[start:]
```

Підпис при цьому **не перевіряється**: для пошуку по тексту це не потрібно, а
видавати корпус за криптографічно звірений було б неправдою. Решта 8 файлів —
звичайні PDF, тому перевірка на `%PDF-` на початку обовʼязкова.

## Як влаштований пошук

**Чанкування по пунктах, а не по символах.** Перший варіант різав текст кожні
900 знаків — і фрагменти починались із середини речення, а один фрагмент містив
три різні пункти договору. Ембединг такого фрагмента — розмита середня тема, і
пошук промахувався. Тому текст спершу збирається назад у пункти (новий пункт
починається з `4.3.19.`, `Стаття 5`, `ІІІ.`, `●`), і вже пункти пакуються у
фрагменти до 400 знаків.

**Стеля фрагмента і різання по реченнях.** Правило «розрив тільки між пунктами»
має зворотний бік: якщо в документі не знайшлось жодного маркера пункту, весь
документ ставав одним фрагментом. Так і вийшло — найбільший фрагмент першої
версії індексу мав **86 523 знаки**, а інвестиційний договір на 37 сторінок був
представлений двома фрагментами по 44 тис. знаків.

Це не косметична вада. У `multilingual-e5-large` `max_seq_length` = **512
токенів** (≈2 000 знаків української), решту токенізатор мовчки відрізає. Заміряв
по всьому індексу: **14,1% тексту корпусу — 188 тис. знаків із 1,33 млн — не
потрапляло в жоден вектор.** Формально документ у базі, фактично не шукається.

Тепер пункт, довший за `CHUNK_CHARS`, ріжеться далі по реченнях, а не по
символах: межа ставиться після `.`, `!`, `?`, `;`, якщо наступний символ —
велика літера, лапка або цифра, і якщо слово перед крапкою не абревіатура
(`п.`, `ст.`, `грн.`, `тис.` — інакше «п. 6.4.2» розпалось би на два фрагменти).
Речення пакуються назад до 400 знаків; на випадок, коли одне «речення» — це
рядок таблиці без крапок узагалі, є жорстка стеля `CHUNK_MAX=1200` з розривом по
пробілу. Найдовший фрагмент тепер — **301 токен**, тобто обрізання немає ніде.

**Скільки тут насправді «по пунктах».** Формулювання вище легко переоцінити, тому
цифри по готовому індексу:

| Як утворився фрагмент | Частка |
|---|---|
| рівно один цілий пункт | 28% |
| кілька коротких пунктів разом | 24% |
| шматок довгого пункту, різаний по реченнях | **48%** (54% тексту) |

Причина — у розподілі самих пунктів: медіана **174 знаки**, максимум **86 523**,
тобто чотири порядки. Лише 20% пунктів довші за 400 знаків, але саме в них лежить
**65% тексту корпусу**. Пункт — одиниця змісту й цитування, але не одиниця розміру.
Тому чесна назва підходу — не «різання по пунктах», а ієрархія: **структура
вирішує, де різати можна, бюджет — скільки взяти**.

**Чому `CHUNK_OVERLAP` тут немає.** Оверлап лагодить конкретну поломку: коли ріжеш
по лічильнику символів, речення розсікається, і в жодній із половин немає повного
твердження — оверлап повертає відрізане. Тут різ проходить лише по межах пунктів і
речень, тож розсіченого твердження просто немає, і повертати нічого.

Перевірив, а не припустив: побудував паралельний індекс з оверлапом 150 і прогнав
ті самі калібрувальні питання. Фрагментів стало 3 771 замість 3 668, топ-1
змінився у 8 випадках з 22, але **жоден бал не зрушив більше ніж на 0.005** — і
двічі на гірше. «Скільки відсотків кешбеку я отримаю?» впало з 0.8606 до 0.8557,
бо оверлап приліпив спереду «Програма лояльності діє виключно для Клієнтів —
фізичних осіб» і розмив вектор. Одиниця оверлапу тут — цілий пункт, а не 150
випадкових символів, тож він підмішує в один вектор другу тему.

**Parent-document retrieval — те, що справді бракувало.** Різ по реченню не
розсікає твердження, але довгий пункт усе одно розкладається на кілька фрагментів,
і кожен із них окремо втрачає контекст: «У цьому випадку Банк списує кошти
протягом 3 днів» без сусіда не пояснює, що таке «цей випадок».

Тому пошук і видача розведені: **шукається дрібний фрагмент, а віддається пункт.**
Кожен фрагмент памʼятає свій батьківський пункт (`parent`), і `search_docs` після
ранжування добирає сусідів з тієї ж родини — по одному вліво і вправо, доки
сумарно вкладається в `PARENT_CHARS`. Точність пошуку лишається від дрібного
фрагмента, повнота — від пункту. Для монструозних пунктів видача обрізається
бюджетом і чесно позначається: `"context": "показано 4 з 201 частин пункту"`.

Що це змінило на практиці — питання «Магазин списав більше, ніж я купив — як
оскаржити?». До цього агент цитував лише п. 6.3.4.2 про зарахування коштів до
розгляду претензії. Після — дістав із того самого пункту сусідів і додав те, що
насправді найважливіше:

```
Подати претензію треба не пізніше 90 календарних днів з дати операції... Якщо не
встигнути, операція вважається підтвердженою й оскаржити її далі не можна
(Умови і правила, п. 6.1.5).
```

Банк не пише «загубив» — банк пише «втрата платіжного інструменту». Це рівно та
сама пара, що «загубили посилку» проти «втраченого відправлення», тільки знайдена
у справжньому документі, а не придумана для прикладу.


BM25 має найвищий бал `13.66` — і це пункт **«Не робити операцій, пов'язаних з
порушенням законодавства»**. З чого цей бал склався:

| Слово запиту | tf у фрагменті | df (фрагментів із 3 668) | IDF | Внесок у бал |
|---|---|---|---|---|
| `загубив` | 0 | **0** | 0.00 | 0.0000 |

Головне слово запиту дало **нуль**: його немає в корпусі взагалі. А 70% бала дало
слово «робити» — і саме тому, що воно рідкісне. Канцелярит його не вживає, тож
воно трапилось рівно в одному фрагменті з 3 668 і отримало найвищий можливий IDF.
Довжина теж підіграла: 23 слова проти середніх 38,2 по базі, а нормалізація по
довжині піднімає короткі фрагменти. BM25 відпрацював свою логіку бездоганно — і
назвав найбезмістовніше слово питання найінформативнішим сигналом.

Морфологія добиває окремо: навіть якби документ казав «загублена картка», токен
`загубив` усе одно не збігся б — стемінгу тут навмисно немає, щоб baseline був
чесним «пошуком по словах».

Ембединги на позиціях 2 і 3 дістають саме визначення втрати картки і підставу для
її блокування, не маючи з запитом жодного спільного слова.

Далі агент відповідає з посиланням на пункт:

```

                            при втраті", "top_k": 5}

  [2] search_docs {"query": "Як повідомити банк про втрату картки та подати заяву
                            на блокування, куди звертатися", "top_k": 6}
      → 6 фрагментів · найкращий 0.8714: Умови і правила ... п. 6.4.2

Стан: ok · кроків: 2 · 43.09 с · токени 5561→1183

Головне — якнайшвидше повідомити банк про втрату, щоб картку заблокували. За
правилами, коли банк отримує вашу заяву про втрату картки (або ПІН-коду чи телефона,
або якщо реквізити стали відомі третій особі), він блокує платіжну картку та/або
Інтернет-Банк і/або Мобільний застосунок (Умови і правила, п. 6.4.2).

Чого бракує: у документах, які я знайшов, не вказано конкретний канал, куди саме
подати заяву про втрату (кнопка в застосунку, гаряча лінія тощо).
```

Останній абзац — робота правил `guarded`: агент назвав межу знайденого замість
того, щоб дописати правдоподібний номер гарячої лінії.

Агент сам переформулював «загубив» у «при втраті» — але це вже наслідок, а не
причина: пошук по змісту знаходить потрібне і на сирому формулюванні, що видно
з порівняння вище, де жодного переписування не було.

### Де BM25 виграє — і чому в проді роблять гібрид

Чесно про межі: ембединги виграють не завжди. На питанні «Чи можу я дати
чоловікові доступ до свого рахунку?» BM25 другим результатом дістає потрібний
пункт про **Картку довіреної особи** (збіг по слову «доступ»), а ембединги
топляться в розділі про Відкритий банкінг. Пошук по словах точний там, де
користувач випадково вжив термін документа; пошук по змісту виграє там, де не
вжив. У цьому проєкті два режими лишені чистими й не змішані, щоб різниця між
ними була видима на однакових даних.

## 2. Агент чесно каже «не знаю»

Питання **«Які документи потрібні, щоб оформити військову пенсію?»** звучить як
питання до банку, але у 18 документах відповіді на нього немає.

### Було (`--rag naive`)

Мінімальний системний промпт («ти асистент monobank, відповідай стисло») плюс
`search_docs`, який завжди повертає 5 найближчих фрагментів — без порога:

```
Запит: «Які документи потрібні, щоб оформити військову пенсію?»
Модель: qwen3.8-max · база знань: naive

  [1] search_docs {"query": "Які документи потрібні для оформлення військової пенсії"}
      → 5 фрагментів · найкращий 0.8156: Умови і правила ...

Стан: ok · кроків: 1 · 36.69 с · токени 2427→609

Це питання не в компетенції банку — оформленням військових пенсій займається
**Пенсійний фонд України**.

Заяву та документи зазвичай подають через військову частину або ТЦК та СП за місцем
перебування на військовому обліку. Орієнтовний пакет: паспорт, РНОКПП,
військово-лікарська комісія/документи про звільнення зі служби, довідка про грошове
забезпечення, документи про вислугу років.

Точний актуальний перелік краще уточнити безпосередньо в Пенсійному фонді: на сайті
**pfu.gov.ua** або за телефоном контакт-центру **0 800 503 753**.
```

Інструмент відпрацював чесно: повернув пʼять фрагментів із найкращою схожістю
0.8156 — уривки про ідентифікацію дитини й підтвердження фінансового стану, тобто
нічого по темі. Модель це побачила, сказала «не в компетенції банку» — і одразу
видала повний перелік із памʼяті, разом із номером телефону. Перевірка по корпусу:

| Що названо у відповіді | Входжень у 18 документах |
|---|---|
| `військовий квиток` | **0** |
| `грошове забезпечення` | **0** |
| `вислуг` (вислуга років) | **0** |
| `pfu.gov.ua`, телефон `0 800 503 753` | **0** |

Це і є головний баг: **агент з підключеним пошуком відповів не з пошуку.**
Формально він навіть попередив, що в документах цього немає — і саме тому
відповідь небезпечна: попередження губиться в першому абзаці, а список під ним
виглядає як витяг із бази. В іншому прогоні того самого питання в тому самому
режимі він узагалі не викликав інструмент і відповів одразу.

### Стало (`--rag guarded`)

```
Запит: «Які документи потрібні, щоб оформити військову пенсію?»
Модель: qwen3.8-max · база знань: guarded

  [1] search_docs {"query": "Які документи потрібні для оформлення військової пенсії"}
      → 0 фрагментів (найкраща схожість 0.8156 < поріг 0.83)

Стан: ok · кроків: 1 · 9.49 с · токени 1489→283

У документах, які я маю, цього немає. Моя база містить лише документи про банківські
послуги monobank | Universal Bank: умови й правила, тарифи, кешбек, кредити,
облігації та сервіси, тож підказати перелік документів для оформлення військової
пенсії не зможу.
```

Той самий інструмент, той самий бал 0.8156, та сама модель — різниця лише в тому,
що інструмент цього разу сказав «нічого», а правила заборонили добудовувати.

`found: 0` тут не детермінований: агент щоразу формулює запит трохи інакше, і в
іншому прогоні він спитав «…для оформлення військової пенсії **у банку**», отримав
0.8362, два фрагменти пройшли поріг — і відмову дали вже правила, а не число.
Обидва запобіжники по черзі беруть на себе те саме питання, і саме тому потрібні
обидва.

### Що саме полагоджено

Три запобіжники: два на вході в модель, один на виході.

**1. Інструмент вміє повертати «нічого».** Наївний `search_docs` завжди віддає
`top_k` фрагментів: навіть на питання про футбол він поверне пʼять шматків
договору з балами 0.742 — і модель отримає сигнал «щось знайшлося». Тепер бали
нижчі за поріг відрізаються, і замість фрагментів приходить прямий факт:

```json
{"query": "...", "found": 0, "fragments": [],
 "best_score": 0.8156, "threshold": 0.83,
 "note": "У базі немає фрагмента, достатньо близького до запиту: найкраща схожість
          0.8156, поріг 0.83. Це означає «в документах цього немає», а не «шукай інакше»."}
```

**2. Промпт забороняє добудовувати.** Правила режиму `guarded` вимагають
відповідати виключно фрагментами, супроводжувати кожне твердження посиланням на
документ і пункт, а на `found: 0` — зупинятись.

**3. Відповідь віддається через інструмент, який звіряє цитати.** Перші два
запобіжники стоять на вході в модель. Третій — на виході: у режимі `guarded`
відповідь на питання про документи не пишеться текстом, а подається викликом
`submit_answer` ([domain/tools.py](domain/tools.py)), де кожне твердження несе
дослівну цитату з фрагмента:

```json
{"answer": "Якщо ви загубили картку, її потрібно негайно заблокувати...",
 "claims": [{"text": "Банк блокує картку після заяви клієнта про втрату",
             "quote": "При отриманні заяви Клієнта (Держателя) блокувати Платіжну
                       картку та / або Інтернет-Банк та/ або Мобільний застосунок
                       в зв'язку з втратою Платіжної картки...",
             "doc": "Умови і правила обслуговування в АТ «Універсал Банк»",
             "clause": "6.4.2"}]}
```

Інструмент шукає кожен `quote` у фрагментах, які `search_docs` реально видав у
цьому прогоні, і звіряє його з полем `clause`. Це порівняння підрядків, а не
судження — тому воно не залежить від моделі:

| Що подала модель | Відповідь інструмента |
|---|---|
| дослівна цитата з потрібного пункту | `delivered: true` |
| переказ своїми словами | `цитати немає у жодному виданому фрагменті` |
| правильна цитата, але чужий номер пункту | `цитата є у видачі, але не в пункті 1.1.1` |
| `claims: []` (відмова «цього немає») | `delivered: true` |
| твердження без жодного виклику `search_docs` | `no_fragments` |

Відхилення — це помилка інструмента, тобто звичайний крок циклу: модель отримує
перелік непідтверджених тверджень і складає відповідь наново. Ось прогін, де
це справді сталося: перша спроба `submit_answer` не пройшла, друга принесла
чотири підтверджені цитати.

```
  [1] search_docs {"query": "Як оскаржити операцію за карткою..."}
      → 6 фрагментів · найкращий 0.8641: Умови і правила ... п. 6.3.4.2
  [2] search_docs {"query": "Куди і як подати заяву про оскарження операції..."}
      → 6 фрагментів · найкращий 0.8732: Умови і правила ... п. 6.1.5
  [3] submit_answer {"answer": "Оскаржити списання можна так...", "claims": [...]}
      → відповідь прийнято, підтверджених цитат: 5

Стан: ok · кроків: 3 · 74.65 с · токени 5516→2997
Звірка цитат: 5 підтверджено видачею
```

Різниця з перших двох запобіжників принципова: промпт — це прохання, а тут
модель **не може** віддати твердження, якого немає у видачі. Не «їй не радять» —
інструмент його не приймає.

Межі цього механізму:

- Звіряється дослівність цитати і її прив'язка до пункту, а не те, чи `text`
  твердження відповідає цитаті. Модель може підставити правильну цитату під
  неточне формулювання.
- Механізм працює тільки в `guarded`: у `naive` інструмента `submit_answer`
  немає, відповідь пишеться текстом.
- Відповіді про гроші (`get_statement`) віддаються текстом: там числа рахуються
  з операцій, і дослівна цитата не має сенсу. Для таких прогонів рядка звірки
  немає.
- Довгі дослівні цитати з'їдають вихідні токени: на відповіді з чотирьох
  тверджень `MAX_TOKENS=1500` обривав виклик посеред аргументів, тому ліміт
  піднято до 3000.

### Калібрування порога: чому одного числа мало

Поріг вибирався не «на око», а по двох наборах питань: 10 таких, відповідь на
які в базі є, і 8 таких, яких там немає. Заміряний топ-1 бал:

| Набір | Мінімум | Максимум |
|---|---|---|
| Відповідь у базі є (10 питань) | 0.8431 | 0.8744 |
| Відповіді немає (8 питань) | 0.7422 | 0.8755 |

**Діапазони перетинаються.** «Як переказати біткоїн з monobank?» дає 0.8755 —
вище за будь-яке питання з бази, бо в документах справді є багато тексту про
перекази, просто не про криптовалюту. Жодне значення порога не розділить ці два
набори: близька тема і наявна відповідь виглядають для косинуса однаково.

Тому поріг ловить лише **далеке** (погода 0.766, футбол 0.742, військова пенсія
0.816, банківський сейф 0.805, відділення в Харкові 0.825), а **близьке, але
відсутнє** (іпотека 0.859, криптовалюта 0.876, рахунок у Польщі 0.853,
автокредит 0.842) лишається на промпті. Обидва прогони нижче — питання з балами
вище порога, де відмову дали правила, а не число:

```
Запит: «Скільки коштує оренда індивідуального банківського сейфа в monobank?»
  [1] search_docs → 5 фрагментів · найкращий 0.8615: Тарифи ...
  У знайдених фрагментах є інформація про депозити, сервіс накопичення «Банка» та
  сервіс «Єчек», але жодних даних про оренду індивідуального банківського сейфа
  чи її вартість там немає.

Запит: «Чи можна оформити туристичну страховку для подорожі за кордон у monobank?»
  [1] search_docs → 5 фрагментів · найкращий 0.8455: Тарифи ...
  Я перевірив базу документів monobank, але інформації саме про туристичне
  страхування для подорожей за кордон там немає. Знайшлися лише фрагменти про
  перекази за кордон, депозити та інші послуги.
```


### Поріг оцінює запит моделі, а не запит користувача

Агент переформулює запит перед пошуком, і бал змінюється разом із формулюванням,
хоча база й саме питання ті самі:

| Формулювання | Бал | Вердикт при 0.83 |
|---|---|---|
| «Скільки коштує оренда банківського сейфа?» | 0.8047 | `found: 0` |
| «…індивідуального банківського сейфа в monobank, **тарифи** на послугу зберігання цінностей» ← так спитав агент | 0.8615 | проходить |
| «Чи можна оформити студентський кредит на навчання?» | 0.8203 | `found: 0` |
| «Студентський кредит: чи можна оформити кредит на оплату освіти» ← так спитав агент | 0.8255 | `found: 0` |
| «умови кредитування студентів на освіту» | 0.8416 | проходить |

Слово «тарифи» піднімає бал на 0.057 — воно підтягує документ «Тарифи», у якому
сейфів немає взагалі. Тобто **бал виріс від слова, яке не наблизило відповідь**.
У прогоні вище саме тому спрацював не поріг, а правило: фрагменти прийшли, і
агент мусив сам сказати, що відповіді в них немає.

Висновок той самий, що й у челенджі A, тільки з іншого боку: **запобіжник, який
залежить від формулювання запиту, не можна лишати єдиним.** І калібрувати поріг
на питаннях, які пише людина, теж некоректно — оцінюється текст, який згенерувала
модель.

### Ціна відмови

Поріг ріже і корисне. Питання «Магазин списав більше, ніж я купив — як
оскаржити?» дає 0.8343: ембединги знаходять саме потрібний пункт 6.3.4.2 про
оскарження операції до 100 000 грн, а BM25 на першому місці має пункт про
зберігання персональних даних з інвестиційного договору. Це відповідь, яка в базі
є, — і вона проходить поріг із запасом усього 0.004.

Звідси видно, наскільки вузьке вікно, у якому взагалі можна поставити число:

| Межа | Значення | Що її задає |
|---|---|---|
| знизу | 0.8246 | «Чи є в monobank відділення в Харкові?» — найвище з того, що ще ловиться |
| **обрано** | **0.83** | |
| зверху | 0.8343 | «як оскаржити покупку» — найнижче питання, відповідь на яке в базі є |

Вікно шириною 0.01 на шкалі, де значення лежать у діапазоні 0.74–0.88. Підняти
поріг на два соті — і агент почне відмовляти на питаннях, які може закрити;
опустити на два соті — і повз пройде військова пенсія. Це не налаштування, яке
можна «підкрутити на око», і не те, що переживе зміну моделі ембедингів або
поповнення корпусу: обидві межі виміряні на конкретному індексі й мусять
перевимірюватись разом із ним.

# Модуль 4 · Мультиагентність: чи вартий роутер свого виклику

Четвертий модуль курсу пропонує сім патернів мультиагентних систем і скрипт
[`choose_pattern.py`](https://github.com/sanyaden/agents0826/blob/main/module4/choose_pattern.py),
який шістьма питаннями підбирає патерн під задачу. Прогнав майстер реальними
відповідями під профіль mono-agent (не вгадуючи — звірено з кодом):

| Питання | Відповідь | Чому |
|---|---|---|
| Запити різних типів, кожен по-своєму? | так | гроші (monobank API) і правила банку (RAG) — різні світи ще в бізнесі |
| Частини задачі незалежні? / строгі етапи? | ні | |
| Є обʼєктивний критерій «добре/погано»? | так | цитата має дослівно збігатись із виданим фрагментом |
| Незворотні дії? | ні | агент лише читає |
| Памʼять між розмовами? | ні | кожен запуск одноразовий |

Результат майстра — **Supervisor/Router** зверху, і скрипт сам додав підказку:
раз є критерій якості, «всередині воркера доречна петря критика»
(Evaluator–Optimizer). Мережу (`network`) інструмент не радить ніколи за
дизайном.

## Патерн 1 — Router: гроші й документи як два спеціалісти

До цього модуля один агент тримав ОБИДВА набори інструментів (`list_accounts`,
`get_statement`, `search_docs`, `submit_answer`) в одному системному промпті —
`core/agent.py` + `config.system_prompt()`. Тепер `core/router.py` спершу
класифікує запит дешевим викликом (`max_tokens=20`, `thinking: disabled`) на
`finance` / `policy` / `other`, і веде до спеціаліста з вузьким промптом і
лише своїми інструментами:

```bash
python run.py "скільки я витратив учора" --router
python demo.py 11
```

### Чому в спеціалістів різні права, а не спільний набір

| Спеціаліст | Інструменти | Чому саме ці |
|---|---|---|
| `finance` | `list_accounts`, `get_statement` | рахує гроші з виписки, тексту документів не потребує; `submit_answer` не дає — там немає що цитувати, суми не є цитатою |
| `policy` | `search_docs`, `submit_answer` | відповідає ВИКЛЮЧНО фрагментами з бази, тому обидва інструменти йдуть парою: без `submit_answer` нема кому звірити цитату |
| `other` | — (порожній список) | привітання й питання про самого агента не потребують жодного джерела даних; порожній `tools=[]` перевірено — Anthropic API приймає його без помилки |

Це не довільний поділ, а той самий принцип найменших прав, що вже діє в
`domain/tools.py`: `ARITHMETIC_TOOLS` (гроші) і `DOC_TOOLS` (документи) в
`core/verify.py` розрізняються ще з модуля 2 — тепер цей поділ підняли з
рівня верифікації на рівень доступу.

### Що робить роутер, якщо тип не розпізнано

`core/router.py` приймає лише три мітки. Усе інше — порожній рядок, зайве
слово, збій виклику — падає у сентинел `"both"`, і запит іде через
**оригінальний комбінований промпт і всі інструменти разом**, тобто в режим
до модуля 4. Це не гіпотетична гілка: саме так провалилась перша версія
роутера — з `max_tokens=8` модель обривалась на `ThinkingBlock`, жодного
слова категорії не долітало, і `classify()` на всіх трьох тестових запитах
чесно повертала `"both"` замість здогадки. `report.route()` показує це
явно: `«both — роутер не впізнав категорію, fallback на єдиного агента»`.
Найбезпечніша відповідь на нерозпізнаний тип — не вгадувати спеціаліста, а
віддати запит тому, хто вміє все.

### Перша спроба зробити виклик класифікації дешевим не спрацювала

Очікував, що `max_tokens=8` вистачить на одне слово. На `qwen3.8-max`
(reasoning-модель) відповідь щоразу обривалась на `ThinkingBlock` до появи
самого слова — `stop_reason: max_tokens`, жодного `TextBlock`. Перевірено
живим викликом:

```
max_tokens=8    → [ThinkingBlock(...)]                          · stop_reason=max_tokens
max_tokens=200  → [ThinkingBlock(139 токенів роздумів), 'finance'] · 130→139 токенів
```

Класифікація в одне слово коштувала стільки ж, скільки короткий хід агента —
«дешевий виклик» на роутер не виправдовувався. Рішення знайшлось не в
збільшенні бюджету, а в параметрі `thinking: {"type": "disabled"}` (штатний,
не бета-тип SDK `anthropic` 0.122 — `thinking_config_disabled_param.py`):

```
thinking: disabled → 'finance' · 94→1 токен
```

Один вихідний токен на класифікацію. Тепер `core/router.py` завжди передає
`thinking: disabled` у виклик роутера.

### Роутер помилився — і мовчки прибрав запобіжник

П'ять калібрувальних запитів дали один справжній збій: «Магазин списав
більше, ніж я купив — як оскаржити?» роутер класифікував як `finance`
(стабільно, перевірено повторно), хоча це питання до `policy` — про
процедуру оскарження з Умов і правил.

Небезпечний не сам мисклас, а те, що сталось далі. FINANCE-спеціаліст не має
`search_docs` і не має правил `DOCS_GUARDED` («відповідай ВИКЛЮЧНО тим, що є
у фрагментах») — вони лежали в `policy_prompt()`, а не в `finance_prompt()`.
Отримавши питання не зі своєї теми, він **не відмовився**, а впевнено видав
вигаданий пʼятикроковий алгоритм оскарження з памʼяті:

> «Банк ініціює процедуру чарджбеку: звʼяжеться з банком-екваєром... Зазвичай
> це займає від кількох днів до кількох тижнів»

Жодної цифри звідси немає в жодному з 18 документів. Це рівно та відповідь,
яку весь проєкт мав не давати — тільки цього разу її спричинив не промпт, а
топологія: розклавши один агент на спеціалістів, я забрав запобіжник
«не вигадуй» із фінансового спеціаліста разом із рештою `DOCS_GUARDED`, бо
вважав його правилом бази знань, а не загальним правилом системи.

Полагоджено додаванням до ОБОХ спеціалістів спільного рядка `BOUNDARY`:
якщо питання поза межами доступних інструментів — сказати прямо, а не
добудовувати. Мисклас лишився (роутер і далі веде на `finance`), але
результат тепер безпечний:

```
До:    «Ось що варто зробити, щоб оскаржити зайве списання: 1. Перевірте...»
Після: «Оскарження операцій — це не моя частина системи: у мене є лише
        доступ до виписок по рахунках, без знання банківських процедур.
        За самою процедурою звернись до підтримки в застосунку.»
```

Висновок симетричний із рештою проєкту: **межу «не вигадуй» треба ставити на
кожного спеціаліста окремо, а не як спільне правило одного агента** — router
розбиває один промпт на кілька, і кожен уламок мусить самостійно нести
власні запобіжники, інакше помилка маршрутизації тихо знімає їх.

## Патерн 2 — петля критика: явний ліміт замість прихованого

`submit_answer` (модуль 2) і так відхиляв непідтверджені цитати, а модель
переформульовувала відповідь у наступному ході — де-факто Evaluator–Optimizer.
Але лічильника не було: відхилення просто споживало кроки із загального
`MAX_TURNS`, спільного з рештою розмови.

Тепер `core/agent.py` рахує `critic_attempts` — відхилення саме
`submit_answer` — окремо від ходів циклу. Після `MAX_CRITIC_ATTEMPTS`
(за замовчуванням 2) агент не мовчки витрачає бюджет далі, а зупиняється
новим станом `critic_exhausted`: одним фінальним викликом без інструментів,
що просить підсумувати підтверджене й назвати непідтверджене — той самий
принцип graceful degradation, що і в `turns_exhausted`.

Перевірено примусово (`domain.tools.IMPL["submit_answer"]` підмінено на
функцію, що завжди відхиляє — `demo.py`, сцена 12): після двох відхилень
цикл зупинився сам, `critic_attempts: 2`, і модель чесно розділила відповідь
на підтверджене й непідтверджене замість того, щоб продовжувати спроби чи
мовчки здатись.

```bash
python demo.py 12
```

## Патерн, який відхилено виміром: паралельний гібридний пошук

Третій кандидат — `domain/kb.py` вже має окремо `semantic()` і `keyword()`
(BM25), але поєднує їх лише в `search.py` для порівняння. Ідея: справжній
Parallel + Aggregator — запускати обидва і зливати результат (Reciprocal Rank
Fusion, `k=60`) у сам `search_docs`.

Перевірив на трьох калібрувальних запитах із модуля 2, де очікуваний пункт
відомий заздалегідь:

| Запит | Очікується | semantic-only top-1 | RRF-злиття top-1 |
|---|---|---|---|
| «Я загубив картку, що робити?» | п. 6.4.2 (про втрату) | **влучив**, 0.856 | промах — «лід з кокпіту літака» |
| «Магазин списав більше — як оскаржити?» | п. 6.3.4.2 | **влучив**, 0.832 | промах на 1 місце (2.9.17), правильний — 2-й |
| «Чоловікові доступ до рахунку?» | Картка довіреної особи | промах (немає в топ-5) | теж промах — топ-1 RRF нерелевантний |

Гіпотеза не підтвердилась: наївне рівновагове злиття **погіршило** два з
трьох випадків, де семантичний пошук сам справлявся, і не витягнуло третій,
де мав допомогти BM25 (сирий `keyword()` дійсно знаходить «Картку довіреної
особи» на 2-му місці за словом «доступ» — RRF цей сигнал загубив під шумом
BM25-фальшивих спрацювань на кшталt «поповнення валютної картки»). Причина
та сама, що вже описана вище для чистого BM25: без стемінгу й фільтрації
рідкісні слова-фальшспрацювання отримують завищений IDF і забивають
релевантний сигнал навіть у злитті.

Патерн **не увімкнено** в `search_docs`. Тюнити зважене злиття (не 50/50, а
з довірою до семантики за замовчуванням і BM25 як tie-breaker) — окрема
задача калібрування, така сама за обсягом, як підбір порогу 0.83 в модулі 2,
і не виправдана третім патерном «про запас». Чесний негативний результат тут
цінніший за впроваджений, але непроміряний код.

## Вимірювання: один агент проти системи на пʼяти запитах

```bash
python compare.py
```

Ті самі пʼять запитів (money-ланцюжок, документ, чат про агента, документ
на межі маршрутизації, порожній період) через нинішній єдиний агент і через
router. Один прогін на варіант, без повторів — тому числа орієнтовні, а не
статистично вивірені (на відміну від калібрування порога 0.83 в модулі 2,
де вимір ішов по 18 запитах).

| Запит | single agent | router |
|---|---|---|
| «Скільки я витратив за минулий тиждень?» | ok · 4347→1447 · 30.7 с | finance · ok · 4266→1776 · 38.9 с |
| «Я загубив картку, що робити?» | ok · 3412→649 · 29.4 с · перевірка OK | policy · ok · 7586→1502 · 35.1 с · перевірка OK |
| «Привіт! Розкажи, що ти вмієш» | no_tool_used · 1031→462 · 11.5 с | other · no_tool_used · 326→329 · 13.6 с |
| «Магазин списав більше — як оскаржити?» | ok · 2572→1811 · 37.0 с · перевірка OK | finance (мисклас!) · no_tool_used · 273→221 · 8.4 с |
| «Що я купував між 3 і 4 ранку?» | ok · 4597→1222 · 26.4 с | finance · ok · 3441→1641 · 39.8 с |
| **Разом** | **21 550 токенів · 135.0 с** | **21 361 токенів (−0.9%) · 135.8 с (+0.6%)** |

**Вартість.** Прогони зняті на QwenCloud, реальний рахунок за них невідомий —
у README рахую за офіційним курсом `claude-sonnet-4-6` (`config.py`'s
дефолтна модель, $3 / $15 за MTok вхід/вихід, [платна документація
Anthropic](https://platform.claude.com/docs/en/about-claude/pricing),
перевірено живим запитом до сторінки): single agent — **$0.1317**, router —
**$0.1297** (−1.5%). Вартість і токени розходяться на соті відсотка, бо
вихід коштує в 5 разів дорожче за вхід, а в роутера він трохи легший.

**Скільки відповідей реально закривають питання клієнта.** Single agent —
**5 з 5**: навіть на четвертому запиті агент знайшов і процитував пункт
6.3.4.2. Router — **4 з 5**: на тому самому запиті мисклас віддав його
FINANCE-спеціалісту, і клієнт отримав чесну, але непотрібну йому відмову
замість відповіді по суті. Токенова економія роутера на цьому запиті
($0.004) не покриває того, що клієнт нічого не дізнався.

Router **не** виграв переконливо, і це чесний результат, а не провал вимірю.
Токени й час практично зрівнялись: економія на `other` й частині
`finance`-запитів з'їдається тим, що POLICY-спеціаліст цього разу зробив на
один `search_docs`-виклик більше за комбінованого агента, а мисклас на
четвертому рядку взагалі не дав відповіді на питання — просто дешево
відмовився. Це і є задокументована в `choose_pattern.py` ціна: «+1 дешевий
виклик на класифікацію; помилка роутера = не той спеціаліст». На вибірці з
пʼяти запитів і одного домену на два спеціалісти ця ціна поки не окупається —
`mas_rag.py` курсу показує, що вигода від ізоляції контексту приходить із
масштабом (14 проти 210 правил), а тут два вузькі спеціалісти й так короткі.
**Для mono-agent сьогодні чесна відповідь — той самий «Правило 2026»
дефолт: єдиний агент лишається основним режимом, router — задокументована
альтернатива для порівняння, а не заміна.**

## Висновок: кому з них довірив би реальних клієнтів

**Single agent.** 5 з 5 запитів закрито по суті, дешевше за router на
вартості (на цій вибірці — символічно, $0.0020), і немає нового класу
збоїв: усе, що може піти не так, — це вже описані `tool_error` /
`turns_exhausted` / `critic_exhausted`, кожен з яких відомий і граціозно
деградує. Router на тій самій вибірці додав РІВНО ОДИН новий спосіб
підвести клієнта — мисклас, — і жодна економія токенів його не покриває,
бо ціна мисклас-у не в токенах, а в невирішеному питанні. Доки в
mono-agent два спеціалісти й пʼять калібрувальних запитів, а не десятки
доменів, я довірив би реальних клієнтів **single agent**. Router вартий
переходу лише якщо зʼявиться третій-четвертий домен (наприклад, окремий
спеціаліст із платежами чи спорами) — там, де `mas_rag.py` курсу і показує
реальний виграш: на масштабі, не на двох сусідніх інструментах.

# Модуль 5 · MCP-сервер: свій інструмент у чужому агенті

У модулях 1–4 «агентом» (циклом, що вирішує, коли й що викликати) завжди був
наш власний `core/agent.py`, а `domain/tools.py` — лише виконавець під його
рукою. Модуль 5 виносить два з цих інструментів за межі власного циклу так,
щоб ними міг скористатись **будь-який** MCP-клієнт — і перевірено це не
здогадкою, а живим запуском особистого Claude Code.

```
Claude Code (MCP-клієнт, чужий agent loop)
        │  stdio JSON-RPC
        ▼
mcp_server.py (MCP-сервер — наш код, тепер по інший бік контракту)
        │  HTTPS + X-Token
        ▼
api.monobank.ua (те саме джерело правди, що і в модулях 1–4)
```

## Що всередині `mcp_server.py`

Два тули, `list_accounts` і `get_statement` — той самий контракт, що вже
відкалібрований у [модулі 1](#модуль-1-основа-ланцюжок-інструментів) (`V2`
у `domain/tools.py`), просто виданий за протоколом MCP замість прямого
виклику з `core/agent.py`.

| Тул | Що робить | Що в описі не випадково |
|---|---|---|
| `list_accounts` | `GET /personal/client-info`: рахунки й банки з `id`, валютою, балансом | «крок 1 з 2» — тільки звідси береться `id`, іншим способом його не дізнатись |
| `get_statement` | `GET /personal/statement/{account}/{from}/{to}` за період | опис параметра `account` прямо забороняє `"0"` (дефолтний рахунок майже ніколи не той, про який питають) і вимагає Unix-час у секундах, а не мс |

Тіла — реальні виклики `domain/mono.py` (HTTP до monobank, помилки як
значення: `401/403/429/timeout` → `{"error": ..., "hint": ...}`, без винятків).
Свідомо **не** імпортується `domain/tools.py` цілком: той тягне за собою
`domain/kb.py → core/embed.py` (sentence-transformers, numpy, індекс бази
знань) — стек пошуку по документах, який фінансовим інструментам не потрібен
і який зробив би сервер залежним від того, чи побудований індекс.

Опис кожного параметра — не докстрінг одним шматком, а
`Annotated[тип, Field(description=...)]`, перевірено живим викликом
`list_tools()` на встановленому пакеті: це дає окремий `description` для
кожного поля в JSON-схемі, так само як уже зроблено для `search_docs` у
`domain/tools.py`.

## Встановлення

```bash
pip install "mcp[cli]"
```

## Inspector

```bash
mcp dev mcp_server.py
```

Піднімає локальний UI в браузері:

1. картка сервера (`uv run --with mcp==2.1.1 mcp run mcp_server.py`) —
   перемикач у "Connected";
2. вкладка **Tools** показує обидва тули, `get_statement` — з трьома полями
   форми, підписаними саме тими описами з `Annotated[..., Field(...)]`, що і
   в коді (не якийсь дефолтний `str`/`int`);
3. **Execute Tool** на `list_accounts` без жодного проміжного клієнта
   повернув реальну відповідь monobank — той самий JSON, що і в тесті нижче
   через Claude Code.

## Підключення до Claude Code

```bash
claude mcp add mono-tools -- "$(pwd)/.venv/bin/python" "$(pwd)/mcp_server.py"
claude mcp list          # mono-tools — ✔ Connected
```

Реєстрація локальна для проєкту (лежить у `~/.claude.json` під шляхом цієї
директорії) — інша сесія Claude Code в іншій директорії сервера не побачить.

## Перевірка

Нова сесія Claude Code (`claude -p`, без жодних інструкцій крім самого
запиту) сама:

1. викликала `list_accounts`, отримала 5 реальних рахунків з реальними
   балансами;
2. **сама вирішила** спершу викликати `list_accounts`, а вже потім
   `get_statement` — цю послідовність ніхто не прописував у промпті, вона
   випливає лише з опису «крок 1 з 2 / крок 2 з 2»;
3. на вигаданому `account="fake123"` отримала не виняток, а структурований
   `{"error": "unknown_account", "hint": "Спершу викликати list_accounts..."}`
   і не зациклилась на тому самому хибному аргументі.

Наш код бачить лише JSON-RPC запит `tools/call` з боку клієнта, про
існування якого не знає нічого, крім опису тулів.

# Структура

```
config.py            ключі з .env, ліміти, правила «не вигадуй», промпти спеціалістів
core/agent.py        цикл «міркуй → дій → спостерігай», стани, петля критика
core/router.py       класифікація запиту → вузький спеціаліст (модуль 4)
core/report.py       друк прогону
core/mask.py         приховування сум для публікації прогонів
core/verify.py       звірка чисел і посилань у відповіді з видачею інструментів
core/embed.py        локальна модель ембедингів, лінива ініціалізація
domain/mono.py       HTTP до monobank, помилки як значення замість винятків
domain/kb.py         корпус → пункти → фрагменти → індекс; пошук по змісту і BM25
domain/tools.py      інструменти моделі: рахунки, виписка, пошук, submit_answer
knowledge/*.md       18 документів банку з фронт-матером (джерело, редакція)
knowledge/.index/    вектори і фрагменти, не в git — будується з корпусу
fetch_knowledge.py   збір корпусу з сайту банку, розпакування підпису КЕП
search.py            CLI бази знань: --build і порівняння двох пошуків
run.py               CLI агента, --router перемикає на маршрутизатор
demo.py              сцени всіх станів, челенджу A, бази знань, роутера й критика
compare.py           один агент проти router на пʼяти запитах, токени пліч-о-пліч
mcp_server.py        MCP-сервер: тули list_accounts і get_statement для будь-якого MCP-клієнта (модуль 5)
```
