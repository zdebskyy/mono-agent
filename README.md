# mono-agent

Агент, який відповідає на питання про власні гроші, спираючись на живий API
monobank — і не вигадує відповідь, коли даних немає.

> «Скільки я витратив учора?» · «Що з моєю банкою на відпустку?» ·
> «Покажи великі покупки за минулий тиждень»

Задача навмисно така, яку **не закрити одним викликом API**: у monobank виписка
запитується не за назвою картки, а за `id` рахунку, і цей `id` віддає лише
окремий метод. Тому кожна відповідь про витрати — це ланцюжок мінімум із двох
кроків, де результат першого є аргументом другого.

```
list_accounts()  →  id рахунку  →  get_statement(account, from_ts, to_ts)  →  відповідь
```

## Як запустити

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

У `.env` вписати два значення:

- `ANTHROPIC_API_KEY` — з console.anthropic.com, `ANTHROPIC_BASE_URL` лишити порожнім
- `MONO_TOKEN` — на https://api.monobank.ua (вхід за QR через застосунок monobank,
  там же кнопка отримання персонального токена)

Ключі читаються **тільки з `.env`**, у коді їх немає, `.env` у `.gitignore`.

### Інший постачальник моделі

Агент говорить протоколом Anthropic Messages, тому працює з будь-яким сервісом,
який цей протокол реалізує — код при цьому не змінюється. Наприклад QwenCloud:

```
ANTHROPIC_API_KEY=<ключ QwenCloud>
ANTHROPIC_BASE_URL=https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic
ANTHROPIC_MODEL=qwen3.8-max
```

Змінна називається `ANTHROPIC_API_KEY`, бо означає «ключ до Anthropic-сумісного
API», а не «ключ, виданий Anthropic». Порожній `ANTHROPIC_BASE_URL` означає
стандартний `api.anthropic.com`.

`.env` читається з `override=True`: якщо в оточенні вже є `ANTHROPIC_BASE_URL`
(його виставляють деякі інструменти), налаштування з файлу мусить перемагати,
інакше запити тихо підуть не туди.

### Команди

```bash
python run.py "скільки я витратив учора"
python run.py "що з моєю банкою" --verbose      # показати сирі відповіді інструментів
python run.py "скільки я витратив за літо" --max-turns 3
python run.py "порахуй витрати на каву" --tools v1
python run.py "скільки я витратив учора" --mask  # приховати суми та id
```

| Прапорець | Навіщо |
|---|---|
| `--tools v1\|v2` | варіант описів інструментів (див. челендж A) |
| `--max-turns N` | ліміт кроків циклу |
| `--model NAME` | інша модель |
| `--verbose` | повні відповіді інструментів, не тільки підсумок |
| `--mask` | замінити цифри в сумах і скоротити `id` — для публікації прогонів |

`--mask` вимкнено за замовчуванням: щодня потрібні справжні числа. Маска чіпає
лише друк — модель у будь-якому разі отримує реальні дані, тому замаскований
прогін лишається справжнім прогоном, а не переказом.

Усі сцени разом відтворює `demo.py`:

```bash
python demo.py          # усі сцени
python demo.py 3 6      # тільки вибрані
python demo.py --mask   # з прихованими сумами
```

| Сцена | Що показує |
|---|---|
| 1 | щасливий ланцюжок `list_accounts` → `get_statement` |
| 2 | `tool_error`: недійсний токен monobank |
| 3 | `turns_exhausted`: питання про літо при ліміті 3 кроки |
| 4 | `api_error`: навмисно зіпсований ключ |
| 5 | `no_tool_used`: питання про самого агента |
| 6 | челендж A: той самий запит на описах `v1` і `v2` |
| 7 | порожній період: `count: 0` замість вигаданих операцій |

## Який API використано

[monobank personal API](https://api.monobank.ua/docs/), автентифікація заголовком
`X-Token`. Факти нижче звірені зі вбудованою OpenAPI-специфікацією (версія `v250818`),
а не взяті з памʼяті.

| Ендпоінт | Що дає | Обмеження |
|---|---|---|
| `GET /personal/client-info` | рахунки (`id`, `type`, `currencyCode`, `balance`) і банки (`jars`) | 1 запит / 60 с |
| `GET /personal/statement/{account}/{from}/{to}` | виписка за період | 1 запит / 60 с; вікно ≤ 2 682 000 с (31 доба + 1 год) |

Дві деталі API визначили дизайн агента:

- **суми приходять у мінімальних одиницях** (копійках), відʼємні — витрати;
  ділення на 100 лишається за моделлю, тому в кожній відповіді інструмента
  є явна примітка про формат;
- **помилки треба читати за HTTP-кодом**, тіло містить `errorDescription`.
  Ліміт 1 запит/60 с означає, що `429` — не екзотика, а звичайний робочий стан,
  який агент мусить пояснити людині.

# Основа

## Ланцюжок

| Інструмент | Аргументи | Повертає |
|---|---|---|
| `list_accounts` | — | рахунки і банки з `id`, валютою, балансом |
| `get_statement` | `account`, `from_ts`, `to_ts` | операції за період |

`get_statement` не можна викликати першим, і це забезпечено **кодом**, а не
проханням в описі: інструмент приймає лише той `id`, який справді прийшов від
`list_accounts` у цьому ж прогоні. Будь-що інше — вигаданий `id`, назва картки,
`0` з документації monobank — повертає `unknown_account`. Реєстр відомих `id`
очищається на початку кожного прогону, тож ланцюжок доводиться проходити щоразу.

## Агент не вигадує даних

Порожній період — це `count: 0` з приміткою, а не помилка: розрізняти
«операцій не було» і «дані не вдалося отримати» агент зобовʼязаний уголос.
Виписка довша за 150 операцій позначається `truncated` з попередженням, щоб
неповна сума не видавалась за повну. У системному промпті числа й назви
дозволено брати виключно з відповідей інструментів.

## Стани агента

Цикл завжди завершується одним із пʼяти станів, і це **повернене значення**,
а не побічний ефект — викликач розгалужується на ньому, а не вгадує з тексту.

| Стан | Коли |
|---|---|
| `ok` | ланцюжок пройдено, відповідь спирається на дані |
| `tool_error` | жоден виклик інструмента не вдався |
| `turns_exhausted` | вичерпано ліміт кроків |
| `api_error` | збій моделі: ключ, мережа, ліміт |
| `no_tool_used` | модель відповіла, жодного разу не звернувшись до банку |

Прогін, який оговтався після невдалого виклику, завершується як `ok`, але зі
списком `failures`: часткова халепа лишається видимою, не стаючи фатальною.

## Ліміт кроків

`MAX_TURNS` (за замовчуванням 6) обмежує кількість обертів циклу. Вичерпання —
не тихий обрив: цикл робить фінальний виклик **без інструментів** і просить
модель підсумувати зібране та назвати, що лишилось недоступним. Якщо падає і
цей виклик — повертається фіксована фраза. У будь-якому разі користувач
отримує відповідь і стан `turns_exhausted`, а не мовчання.

прапорцем `--mask`; модель у прогоні отримувала справжні дані, маска чіпає

# Челендж A · Опис інструмента = поведінка агента

Знайти запит, на якому агент плутає аргументи, полагодити це **описом
інструмента**, і показати прогони до і після.

**Запит:** «Скільки я витратив за останні три місяці?»

**Аргумент, який плутається:** `to_ts` у `get_statement`. monobank віддає
виписку максимум за 31 добу + 1 годину (2 682 000 с). Опис `v1` про це мовчить —
там сказано лише «Останній час виписки», — тож агент замовляє одразу весь
тримісячний період.

**Що змінюється між варіантами.** Виконуваний код інструментів **однаковий**:
та сама функція, та сама валідація, той самий HTTP-запит. Відрізняється рівно
текст опису — тому різниця в поведінці пояснюється описом, а не прихованою
правкою логіки. Перемикається прапорцем `--tools v1|v2`.

### Перша гіпотеза не підтвердилась

Спершу я очікував іншої помилки: специфікація monobank дозволяє передати
`account="0"` («дефолтний рахунок»), і `v1` цю можливість згадує. Здавалося,
агент спокуситься й пропустить `list_accounts`. Прогін це спростував — на
запит «Скільки я витратив у доларах за минулий тиждень?» агент і на `v1`
чесно взяв `id` доларової картки зі списку рахунків.

Тому челендж побудований на помилці, яка справді сталася, а не на очікуваній.

## Опис до (`v1`) — формулювання з офіційної доки

```
get_statement:
  Отримання виписки за період.
    account — Ідентифікатор рахунку або банки з переліку, або 0 — дефолтний рахунок.
    from_ts — Початок часу виписки.
    to_ts   — Останній час виписки.
```

## Висновок

Вирішив **один рядок** — згадка максимального вікна в описі `to_ts`:

```
Максимальне вікно — 2682000 с (31 доба). Довший період розбивати на кілька викликів.
```

До нього агент дізнавався про обмеження єдиним доступним способом — впираючись
у нього, і платив за це пʼятьма марними викликами та зайвими токенами. Після —
обмеження стало частиною умови задачі ще до першого виклику.

Спостереження, яке варте окремої уваги: агент **не переносив** засвоєну помилку
між рахунками. Отримавши `window_too_large` на першому, він повторив той самий
завеликий діапазон ще чотири рази. Тобто помилка інструмента вчить гірше, ніж
опис: опис читається один раз до дії, а помилку доводиться зустріти окремо в
кожній гілці міркування.

Практичний висновок для будь-якого інструмента: **обмеження треба писати в опис
параметра, а не сподіватись, що агент вивчить його з відповіді про помилку.**
