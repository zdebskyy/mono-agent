# mono-agent

Агент, який відповідає на питання про власні гроші й про правила банку, спираючись
на живий API monobank і на 18 публічних документів банку — і не вигадує відповідь,
коли даних немає.

> «Скільки я витратив учора?» · «Що з моєю банкою на відпустку?» ·
> «Я загубив картку, що робити?» · «Яка комісія за переказ в інший банк?»

Два джерела правди, і жодного слова від себе: цифри беруться з виписки, правила —
з чинних Умов і Тарифів із посиланням на пункт. Питання, відповіді на яке немає в
жодному з двох джерел, закінчується словами «цього немає», а не правдоподібним
переказом.

Задача навмисно така, яку **не закрити одним викликом API**: у monobank виписка
запитується не за назвою картки, а за `id` рахунку, і цей `id` віддає лише
окремий метод. Тому кожна відповідь про витрати — це ланцюжок мінімум із двох
кроків, де результат першого є аргументом другого.

```
list_accounts()  →  id рахунку  →  get_statement(account, from_ts, to_ts)  →  відповідь
```

## Як запустити

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

У `.env` вписати два значення:

- `ANTHROPIC_API_KEY` — з console.anthropic.com, `ANTHROPIC_BASE_URL` лишити порожнім
- `MONO_TOKEN` — на https://api.monobank.ua (вхід за QR через застосунок monobank,
  там же кнопка отримання персонального токена)

Ключі читаються **тільки з `.env`**, у коді їх немає, `.env` у `.gitignore`.

Далі — база документів. Корпус уже лежить у `knowledge/`, але векторний індекс
треба побудувати локально (перший запуск тягне ваги моделі ембедингів — 2,1 ГБ
у кеші, ключа для неї не потрібно):

```bash
python search.py --build      # ~100 с на MacBook, одноразово
```

Щоб перезібрати сам корпус із сайту банку — `python fetch_knowledge.py`.

### Інший постачальник моделі

Агент говорить протоколом Anthropic Messages, тому працює з будь-яким сервісом,
який цей протокол реалізує — код при цьому не змінюється. Наприклад QwenCloud:

```
ANTHROPIC_API_KEY=<ключ QwenCloud>
ANTHROPIC_BASE_URL=https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic
ANTHROPIC_MODEL=qwen3.8-max
```

Змінна називається `ANTHROPIC_API_KEY`, бо означає «ключ до Anthropic-сумісного
API», а не «ключ, виданий Anthropic». Порожній `ANTHROPIC_BASE_URL` означає
стандартний `api.anthropic.com`.

`.env` читається з `override=True`: якщо в оточенні вже є `ANTHROPIC_BASE_URL`
(його виставляють деякі інструменти), налаштування з файлу мусить перемагати,
інакше запити тихо підуть не туди.

### Команди

```bash
python run.py "скільки я витратив учора"
python run.py "що з моєю банкою" --verbose      # показати сирі відповіді інструментів
python run.py "скільки я витратив за літо" --max-turns 3
python run.py "порахуй витрати на каву" --tools v1
python run.py "скільки я витратив учора" --mask  # приховати суми та id
python run.py "я загубив картку, що робити"      # питання до бази документів
python run.py "як оформити пенсію" --rag naive   # база знань без запобіжників
```

| Прапорець | Навіщо |
|---|---|
| `--tools v1\|v2` | варіант описів інструментів (див. челендж A) |
| `--rag naive\|guarded` | поведінка пошуку по документах (див. челендж Б) |
| `--max-turns N` | ліміт кроків циклу |
| `--model NAME` | інша модель |
| `--verbose` | повні відповіді інструментів, не тільки підсумок |
| `--mask` | замінити цифри в сумах і скоротити `id` — для публікації прогонів |

`--mask` вимкнено за замовчуванням: щодня потрібні справжні числа. Маска чіпає
лише друк — модель у будь-якому разі отримує реальні дані, тому замаскований
прогін лишається справжнім прогоном, а не переказом.

Усі сцени разом відтворює `demo.py`:

```bash
python demo.py          # усі сцени
python demo.py 3 6      # тільки вибрані
python demo.py --mask   # з прихованими сумами
```

| Сцена | Що показує |
|---|---|
| 1 | щасливий ланцюжок `list_accounts` → `get_statement` |
| 2 | `tool_error`: недійсний токен monobank |
| 3 | `turns_exhausted`: питання про літо при ліміті 3 кроки |
| 4 | `api_error`: навмисно зіпсований ключ |
| 5 | `no_tool_used`: питання про самого агента |
| 6 | челендж A: той самий запит на описах `v1` і `v2` |
| 7 | порожній період: `count: 0` замість вигаданих операцій |
| 8 | питання до бази документів, поставлене іншими словами |
| 9 | ембединги проти BM25 на однакових даних (без моделі) |
| 10 | челендж Б: питання не з бази на `naive` і `guarded` |

## Який API використано

[monobank personal API](https://api.monobank.ua/docs/), автентифікація заголовком
`X-Token`. Факти нижче звірені зі вбудованою OpenAPI-специфікацією (версія `v250818`),
а не взяті з памʼяті.

| Ендпоінт | Що дає | Обмеження |
|---|---|---|
| `GET /personal/client-info` | рахунки (`id`, `type`, `currencyCode`, `balance`) і банки (`jars`) | 1 запит / 60 с |
| `GET /personal/statement/{account}/{from}/{to}` | виписка за період | 1 запит / 60 с; вікно ≤ 2 682 000 с (31 доба + 1 год) |

Дві деталі API визначили дизайн агента:

- **суми приходять у мінімальних одиницях** (копійках), відʼємні — витрати;
  ділення на 100 лишається за моделлю, тому в кожній відповіді інструмента
  є явна примітка про формат;
- **помилки треба читати за HTTP-кодом**, тіло містить `errorDescription`.
  Ліміт 1 запит/60 с означає, що `429` — не екзотика, а звичайний робочий стан,
  який агент мусить пояснити людині.

# Модуль 1 · Основа: ланцюжок інструментів

## Ланцюжок

| Інструмент | Аргументи | Повертає |
|---|---|---|
| `list_accounts` | — | рахунки і банки з `id`, валютою, балансом |
| `get_statement` | `account`, `from_ts`, `to_ts` | операції за період |

`get_statement` не можна викликати першим, і це забезпечено **кодом**, а не
проханням в описі: інструмент приймає лише той `id`, який справді прийшов від
`list_accounts` у цьому ж прогоні. Будь-що інше — вигаданий `id`, назва картки,
`0` з документації monobank — повертає `unknown_account`. Реєстр відомих `id`
очищається на початку кожного прогону, тож ланцюжок доводиться проходити щоразу.

## Агент не вигадує даних

Порожній період — це `count: 0` з приміткою, а не помилка: розрізняти
«операцій не було» і «дані не вдалося отримати» агент зобовʼязаний уголос.
Виписка довша за 150 операцій позначається `truncated` з попередженням, щоб
неповна сума не видавалась за повну. У системному промпті числа й назви
дозволено брати виключно з відповідей інструментів.

## Стани агента

Цикл завжди завершується одним із пʼяти станів, і це **повернене значення**,
а не побічний ефект — викликач розгалужується на ньому, а не вгадує з тексту.

| Стан | Коли |
|---|---|
| `ok` | ланцюжок пройдено, відповідь спирається на дані |
| `tool_error` | жоден виклик інструмента не вдався |
| `turns_exhausted` | вичерпано ліміт кроків |
| `api_error` | збій моделі: ключ, мережа, ліміт |
| `no_tool_used` | модель відповіла, жодного разу не звернувшись до банку |

Прогін, який оговтався після невдалого виклику, завершується як `ok`, але зі
списком `failures`: часткова халепа лишається видимою, не стаючи фатальною.

## Ліміт кроків

`MAX_TURNS` (за замовчуванням 6) обмежує кількість обертів циклу. Вичерпання —
не тихий обрив: цикл робить фінальний виклик **без інструментів** і просить
модель підсумувати зібране та назвати, що лишилось недоступним. Якщо падає і
цей виклик — повертається фіксована фраза. У будь-якому разі користувач
отримує відповідь і стан `turns_exhausted`, а не мовчання.

прапорцем `--mask`; модель у прогоні отримувала справжні дані, маска чіпає

# Модуль 1 · Челендж A: опис інструмента = поведінка агента

Знайти запит, на якому агент плутає аргументи, полагодити це **описом
інструмента**, і показати прогони до і після.

**Запит:** «Скільки я витратив за останні три місяці?»

**Аргумент, який плутається:** `to_ts` у `get_statement`. monobank віддає
виписку максимум за 31 добу + 1 годину (2 682 000 с). Опис `v1` про це мовчить —
там сказано лише «Останній час виписки», — тож агент замовляє одразу весь
тримісячний період.

**Що змінюється між варіантами.** Виконуваний код інструментів **однаковий**:
та сама функція, та сама валідація, той самий HTTP-запит. Відрізняється рівно
текст опису — тому різниця в поведінці пояснюється описом, а не прихованою
правкою логіки. Перемикається прапорцем `--tools v1|v2`.

## Висновок

Вирішив **один рядок** — згадка максимального вікна в описі `to_ts`:

```
Максимальне вікно — 2682000 с (31 доба). Довший період розбивати на кілька викликів.
```

До нього агент дізнавався про обмеження єдиним доступним способом — впираючись
у нього, і платив за це пʼятьма марними викликами та зайвими токенами. Після —
обмеження стало частиною умови задачі ще до першого виклику.

Спостереження, яке варте окремої уваги: агент **не переносив** засвоєну помилку
між рахунками. Отримавши `window_too_large` на першому, він повторив той самий
завеликий діапазон ще чотири рази. Тобто помилка інструмента вчить гірше, ніж
опис: опис читається один раз до дії, а помилку доводиться зустріти окремо в
кожній гілці міркування.

Практичний висновок для будь-якого інструмента: **обмеження треба писати в опис
параметра, а не сподіватись, що агент вивчить його з відповіді про помилку.**

### Сюрприз у форматі: це не PDF

Перелік чинних редакцій віддає `GET /api/info/versioning-docs/{slug}`, самі файли
лежать за `https://monobank.ua/pdf/{fileName}`. Але **10 із 18** цих «pdf» не
відкриваються PDF-бібліотекою:

```
pypdf.errors.PdfReadError: Trailer cannot be read: '/Type'
```

Перші байти файлу пояснюють чому:

```
30 83 29 99 a4 06 09 2a 86 48 86 f7 0d 01 07 02
                  └─ OID 1.2.840.113549.1.7.2 = PKCS#7 signedData
```

Це не PDF, а контейнер із кваліфікованим електронним підписом, усередині якого
лежить PDF. Банк підписує документи КЕП, і на сайт викладає саме підписаний
контейнер із розширенням `.pdf`. Розпаковується він тривіально — вирізанням
від `%PDF-` до останнього `%%EOF`:

```python
def unwrap_signature(raw):
    if raw.startswith(b"%PDF-"):
        return raw
    start = raw.find(b"%PDF-")
    end = raw.rfind(b"%%EOF")
    return raw[start:end + 5] if end > start else raw[start:]
```

Підпис при цьому **не перевіряється**: для пошуку по тексту це не потрібно, а
видавати корпус за криптографічно звірений було б неправдою. Решта 8 файлів —
звичайні PDF, тому перевірка на `%PDF-` на початку обовʼязкова.

## Як влаштований пошук

**Чанкування по пунктах, а не по символах.** Перший варіант різав текст кожні
900 знаків — і фрагменти починались із середини речення, а один фрагмент містив
три різні пункти договору. Ембединг такого фрагмента — розмита середня тема, і
пошук промахувався. Тому текст спершу збирається назад у пункти (новий пункт
починається з `4.3.19.`, `Стаття 5`, `ІІІ.`, `●`), і вже пункти пакуються у
фрагменти до 400 знаків.

**Стеля фрагмента і різання по реченнях.** Правило «розрив тільки між пунктами»
має зворотний бік: якщо в документі не знайшлось жодного маркера пункту, весь
документ ставав одним фрагментом. Так і вийшло — найбільший фрагмент першої
версії індексу мав **86 523 знаки**, а інвестиційний договір на 37 сторінок був
представлений двома фрагментами по 44 тис. знаків.

Це не косметична вада. У `multilingual-e5-large` `max_seq_length` = **512
токенів** (≈2 000 знаків української), решту токенізатор мовчки відрізає. Заміряв
по всьому індексу: **14,1% тексту корпусу — 188 тис. знаків із 1,33 млн — не
потрапляло в жоден вектор.** Формально документ у базі, фактично не шукається.

Тепер пункт, довший за `CHUNK_CHARS`, ріжеться далі по реченнях, а не по
символах: межа ставиться після `.`, `!`, `?`, `;`, якщо наступний символ —
велика літера, лапка або цифра, і якщо слово перед крапкою не абревіатура
(`п.`, `ст.`, `грн.`, `тис.` — інакше «п. 6.4.2» розпалось би на два фрагменти).
Речення пакуються назад до 400 знаків; на випадок, коли одне «речення» — це
рядок таблиці без крапок узагалі, є жорстка стеля `CHUNK_MAX=1200` з розривом по
пробілу. Найдовший фрагмент тепер — **301 токен**, тобто обрізання немає ніде.

| Параметр | Значення |
|---|---|
| Модель ембедингів | `intfloat/multilingual-e5-large`, локально, 1024 виміри |


Агент сам переформулював «загубив» у «при втраті» — але це вже наслідок, а не
причина: пошук по змісту знаходить потрібне і на сирому формулюванні, що видно
з порівняння вище, де жодного переписування не було.

### Де BM25 виграє — і чому в проді роблять гібрид

Чесно про межі: ембединги виграють не завжди. На питанні «Чи можу я дати
чоловікові доступ до свого рахунку?» BM25 другим результатом дістає потрібний
пункт про **Картку довіреної особи** (збіг по слову «доступ»), а ембединги
топляться в розділі про Відкритий банкінг. Пошук по словах точний там, де
користувач випадково вжив термін документа; пошук по змісту виграє там, де не
вжив. Продакшн-відповідь — не «або-або», а гібрид: об’єднати обидва списки і
переранжувати. Тут навмисно лишені два чисті режими, щоб різниця була видима.

## 2. Агент чесно каже «не знаю»

Питання **«Які документи потрібні, щоб оформити військову пенсію?»** звучить як
питання до банку, але у 18 документах відповіді на нього немає.

### Було (`--rag naive`)

Мінімальний системний промпт («ти асистент monobank, відповідай стисло») плюс
`search_docs`, який завжди повертає 5 найближчих фрагментів — без порога:

```
Запит: «Які документи потрібні, щоб оформити військову пенсію?»
Модель: qwen3.8-max · база знань: naive

  [1] search_docs {"query": "Які документи потрібні для оформлення військової пенсії"}
      → 5 фрагментів · найкращий 0.8156: Умови і правила ...

Стан: ok · кроків: 1 · 36.69 с · токени 2427→609

Це питання не в компетенції банку — оформленням військових пенсій займається
**Пенсійний фонд України**.

Заяву та документи зазвичай подають через військову частину або ТЦК та СП за місцем
перебування на військовому обліку. Орієнтовний пакет: паспорт, РНОКПП,
військово-лікарська комісія/документи про звільнення зі служби, довідка про грошове
забезпечення, документи про вислугу років.

Точний актуальний перелік краще уточнити безпосередньо в Пенсійному фонді: на сайті
**pfu.gov.ua** або за телефоном контакт-центру **0 800 503 753**.
```

Інструмент відпрацював чесно: повернув пʼять фрагментів із найкращою схожістю
0.8156 — уривки про ідентифікацію дитини й підтвердження фінансового стану, тобто
нічого по темі. Модель це побачила, сказала «не в компетенції банку» — і одразу
видала повний перелік із памʼяті, разом із номером телефону. Перевірка по корпусу:

| Що названо у відповіді | Входжень у 18 документах |
|---|---|
| `військовий квиток` | **0** |
| `грошове забезпечення` | **0** |
| `вислуг` (вислуга років) | **0** |
| `pfu.gov.ua`, телефон `0 800 503 753` | **0** |

Це і є головний баг: **агент з підключеним пошуком відповів не з пошуку.**
Формально він навіть попередив, що в документах цього немає — і саме тому
відповідь небезпечна: попередження губиться в першому абзаці, а список під ним
виглядає як витяг із бази. В іншому прогоні того самого питання в тому самому
режимі він узагалі не викликав інструмент і відповів одразу.

### Стало (`--rag guarded`)

```
Запит: «Які документи потрібні, щоб оформити військову пенсію?»
Модель: qwen3.8-max · база знань: guarded

  [1] search_docs {"query": "Які документи потрібні для оформлення військової пенсії"}
      → 0 фрагментів (найкраща схожість 0.8156 < поріг 0.83)

Стан: ok · кроків: 1 · 9.49 с · токени 1489→283

У документах, які я маю, цього немає. Моя база містить лише документи про банківські
послуги monobank | Universal Bank: умови й правила, тарифи, кешбек, кредити,
облігації та сервіси, тож підказати перелік документів для оформлення військової
пенсії не зможу.
```

Той самий інструмент, той самий бал 0.8156, та сама модель — різниця лише в тому,
що інструмент цього разу сказав «нічого», а правила заборонили добудовувати.

### Що саме полагоджено

Два запобіжники, і кожен закриває свою половину задачі.

**1. Інструмент вміє повертати «нічого».** Наївний `search_docs` завжди віддає
`top_k` фрагментів: навіть на питання про футбол він поверне пʼять шматків
договору з балами 0.742 — і модель отримає сигнал «щось знайшлося». Тепер бали
нижчі за поріг відрізаються, і замість фрагментів приходить прямий факт:

```json
{"query": "...", "found": 0, "fragments": [],
 "best_score": 0.8156, "threshold": 0.83,
 "note": "У базі немає фрагмента, достатньо близького до запиту: найкраща схожість
          0.8156, поріг 0.83. Це означає «в документах цього немає», а не «шукай інакше»."}
```

**2. Промпт забороняє добудовувати.** Правила режиму `guarded` вимагають
відповідати виключно фрагментами, супроводжувати кожне твердження посиланням на
документ і пункт, а на `found: 0` — зупинятись.

### Калібрування порога: чому одного числа мало

Поріг вибирався не «на око», а по двох наборах питань: 10 таких, відповідь на
які в базі є, і 8 таких, яких там немає. Заміряний топ-1 бал:

| Набір | Мінімум | Максимум |
|---|---|---|
| Відповідь у базі є (10 питань) | 0.8431 | 0.8744 |
| Відповіді немає (8 питань) | 0.7422 | 0.8755 |

**Діапазони перетинаються.** «Як переказати біткоїн з monobank?» дає 0.8755 —
вище за будь-яке питання з бази, бо в документах справді є багато тексту про
перекази, просто не про криптовалюту. Жодне значення порога не розділить ці два
набори: близька тема і наявна відповідь виглядають для косинуса однаково.

Тому поріг ловить лише **далеке** (погода 0.766, футбол 0.742, військова пенсія
0.816, банківський сейф 0.805, відділення в Харкові 0.825), а **близьке, але
відсутнє** (іпотека 0.859, криптовалюта 0.876, рахунок у Польщі 0.853,
автокредит 0.842) лишається на промпті. Обидва прогони нижче — питання з балами
вище порога, де відмову дали правила, а не число:

```
Запит: «Скільки коштує оренда індивідуального банківського сейфа в monobank?»
  [1] search_docs → 5 фрагментів · найкращий 0.8615: Тарифи ...
  У знайдених фрагментах є інформація про депозити, сервіс накопичення «Банка» та
  сервіс «Єчек», але жодних даних про оренду індивідуального банківського сейфа
  чи її вартість там немає.

Запит: «Чи можна оформити туристичну страховку для подорожі за кордон у monobank?»
  [1] search_docs → 5 фрагментів · найкращий 0.8455: Тарифи ...
  Я перевірив базу документів monobank, але інформації саме про туристичне
  страхування для подорожей за кордон там немає. Знайшлися лише фрагменти про
  перекази за кордон, депозити та інші послуги.
```


### Побічний ефект, якого я не очікував

Поріг оцінює не те, що написав користувач. Агент переформулює запит перед пошуком —
і бал змінюється разом із формулюванням, хоча база й саме питання ті самі:

| Формулювання | Бал | Вердикт при 0.83 |
|---|---|---|
| «Скільки коштує оренда банківського сейфа?» | 0.8047 | `found: 0` |
| «…індивідуального банківського сейфа в monobank, **тарифи** на послугу зберігання цінностей» ← так спитав агент | 0.8615 | проходить |
| «Чи можна оформити студентський кредит на навчання?» | 0.8203 | `found: 0` |
| «Студентський кредит: чи можна оформити кредит на оплату освіти» ← так спитав агент | 0.8255 | `found: 0` |
| «умови кредитування студентів на освіту» | 0.8416 | проходить |

Слово «тарифи» піднімає бал на 0.057 — воно підтягує документ «Тарифи», у якому
сейфів немає взагалі. Тобто **бал виріс від слова, яке не наблизило відповідь**.
У прогоні вище саме тому спрацював не поріг, а правило: фрагменти прийшли, і
агент мусив сам сказати, що відповіді в них немає.

Висновок той самий, що й у челенджі A, тільки з іншого боку: **запобіжник, який
залежить від формулювання запиту, не можна лишати єдиним.** І калібрувати поріг
на питаннях, які пише людина, теж некоректно — оцінюється текст, який згенерувала
модель.

### Ціна відмови

Поріг ріже і корисне. Питання «Магазин списав більше, ніж я купив — як
оскаржити?» дає 0.8343: ембединги знаходять саме потрібний пункт 6.3.4.2 про
оскарження операції до 100 000 грн, а BM25 на першому місці має пункт про
зберігання персональних даних з інвестиційного договору. Це відповідь, яка в базі
є, — і вона проходить поріг із запасом усього 0.004.

Звідси видно, наскільки вузьке вікно, у якому взагалі можна поставити число:

| Межа | Значення | Що її задає |
|---|---|---|
| знизу | 0.8246 | «Чи є в monobank відділення в Харкові?» — найвище з того, що ще ловиться |
| **обрано** | **0.83** | |
| зверху | 0.8343 | «як оскаржити покупку» — найнижче питання, відповідь на яке в базі є |

Вікно шириною 0.01 на шкалі, де значення лежать у діапазоні 0.74–0.88. Підняти
поріг на два соті — і агент почне відмовляти на питаннях, які може закрити;
опустити на два соті — і повз пройде військова пенсія. Це не налаштування, яке
можна «підкрутити на око», і не те, що переживе зміну моделі ембедингів або
поповнення корпусу: обидві межі виміряні на конкретному індексі й мусять
перевимірюватись разом із ним.

# Структура

```
config.py            ключі з .env, ліміти, правила «не вигадуй», налаштування бази знань
core/agent.py        цикл «міркуй → дій → спостерігай», пʼять станів
core/report.py       друк прогону
core/mask.py         приховування сум для публікації прогонів
core/embed.py        локальна модель ембедингів, лінива ініціалізація
domain/mono.py       HTTP до monobank, помилки як значення замість винятків
domain/kb.py         корпус → пункти → фрагменти → індекс; пошук по змісту і BM25
domain/tools.py      інструменти для моделі, два варіанти описів
knowledge/*.md       18 документів банку з фронт-матером (джерело, редакція)
knowledge/.index/    вектори і фрагменти, не в git — будується з корпусу
fetch_knowledge.py   збір корпусу з сайту банку, розпакування підпису КЕП
search.py            CLI бази знань: --build і порівняння двох пошуків
run.py               CLI агента
demo.py              сцени всіх станів і обох челенджів
```
